# Trace 新交互演示与组会讲解

## 1. 主线

新项目的关联随 Agent 建模自动建立，用户不需要接受或审核 Trace Link。演示重点是“建模自带来源 → 修改一侧 → 对方出现提醒 → 选择已知晓、手动修改或 AI 修改 → 预览后应用”。

## 2. 会前准备

1. 从仓库根目录运行 `studio.bat`，使用源码开发版。
2. 在 Studio 新建独立演示项目，保存 Informal 与 Hybrid 文件，配置可用模型。
3. 在 Informal 写一个简单的借阅功能，明确输入、输出、成功条件和失败条件。避免使用未经定义的“按借阅政策处理”等模糊规则。
4. 让 Agent 基于该需求增量建立 Hybrid。建议提示：“请基于现有 Informal 建模 Borrow，保留需求中的成功与失败返回码；未明确的规则先问我。”
5. 提前完整彩排，备份整个演示项目，包括 `.agile-sofl/trace`。在线模型结果会变化，只应用你核对过的建议。

最小需求例子：

```text
# Functions
## Borrow
A member borrows a book when member_id > 0 and book_id > 0.
Return success = 1 when both conditions hold; otherwise return success = 0.
- Inputs: member_id (nat), book_id (nat)
- Outputs: success (nat)

# Data Resources

# Constraints
```

## 3. 约 6 分钟的主演示

| 步骤 | 操作 | 讲解 |
|---|---|---|
| 1，建模自带来源 | 展示 Agent 的增量建模结果，应用后点击 Borrow 旁的 ↔ | “系统在应用建模结果时保存来源，不需要再执行一次关联恢复，也没有额外的接受关联步骤。” |
| 2，需求变化 | 将需求中的成功返回码 1 改成 2 | “我按原来的方式编辑。Hybrid 中对应条目出现小圆点，正文还没有被系统改动。” |
| 3，查看提醒 | 点击 Hybrid Borrow 旁的标记 | “这里只需要决定：已知晓、手动修改，或者 AI 修改。” 可展开“查看这次变化”。 |
| 4，AI 修改 | 点击 AI 修改，检查 before / after | “点击 AI 只生成预览，仍未写入。这里核对成功分支返回码是否从 1 改为 2，失败分支是否保持 0。” |
| 5，应用和撤销 | 应用所选修改；使用全局撤销，再重做 | “正文和对应关系一起变化、一起回退。不是把另一个编辑器悄悄覆盖掉。” 离开文本输入焦点后使用全局历史，避免只操作输入框自己的撤销。 |
| 6，反向提醒 | 两侧成功码均为 2 后，将 Hybrid 中成功码改回 1；查看 Informal 的提醒 | “任一侧先改，都会提醒另一侧；在 Informal 的卡片里点 AI 修改，就是反向生成需求修改建议。” |
| 7，已知晓 | 对一处未处理变化点击已知晓，再修改来源 | “已知晓只收起这个版本的提醒，不证明两侧一致；新变化仍会再次提醒。” |

不要以“所有提醒都消失”判断演示成功；只演示当前功能的闭环。模型没有给出合理建议时，应当取消并解释，不强行应用。

## 4. 旧项目放在补充演示

旧项目没有生成来源时，打开“对应内容”，在“已有规格尚未记录来源？”下触发查找。该路径使用论文方法补齐关联，是兼容已有工件的初始化方式，不是新项目每次建模的必要步骤。

不再演示“接受、拒绝、检查、分配、重新关联”等成排管理操作，它们已经从日常界面移除。

## 5. 组会讲解：约 10–12 分钟

1. 问题，1 分钟：两个编辑器分别表达需求和形式化规格，一侧改动后，另一侧哪些条目需要关注？
2. 论文，1 分钟：末级功能、process 与依赖上下文、LLM 语义恢复。它解决已有工件的关联恢复。
3. 本项目设计，1 分钟：新建工件直接保存 Agent 的来源；稳定身份和依赖索引在后台维护；变化只提醒用户，不自动覆盖正文。
4. 现场演示，6 分钟：完成上面的建模、提醒、预览应用和反向变化。
5. 验证与研究计划，1–2 分钟：工程测试验证状态与事务可靠性；下一步用独立标注数据测关联 P/R/F1，再测用户任务时间、AI 建议接受率和人工修改量。

开场可直接说：

> 这次我把 trace link 从需要用户管理的对象，变成编辑器在后台维护的来源关系。Agent 建模时自动记录；后续任一侧修改，用户在另一侧看到提醒，选择已知晓、自己调整或 AI 辅助，AI 的结果仍需预览后应用。

收尾可直接说：

> 论文提供了恢复已有工件关联的方法，这里进一步接入持续建模与编辑。当前能验证的是编辑流程和数据维护机制，真实模型的准确率和用户效率提升还需要单独实验，不能直接沿用论文指标。

## 6. 常见问题

| 问题 | 回答 |
|---|---|
| 新项目也要先找关联吗？ | 不需要。Agent 提交时必须给出明确来源，系统验证后与正文一起保存。 |
| 模型漏掉来源怎么办？ | 工具要求 Agent 补齐；最终应用前还有完整性校验，不先写正文再让用户补关联。 |
| 为什么不直接双向改写？ | 两侧可能都有独立修改，需求还可能一对多。双向绑定用于定位和通知；正文修改仍经过预览。 |
| 已知晓是否代表一致？ | 不代表。只记录本侧看过对方这个版本，保留原同步基线。 |
| 是否达到论文准确率？ | 尚未实测。论文数据与合成回归样例都不能当作本系统真实模型的指标。 |
| 任意拆分、重构都能自动识别吗？ | 明确来源和无歧义身份可以维护；无法确定时不能凭名字猜测。系统保留历史身份并阻止缺来源的新建模结果。 |

## 7. 网络备用

真实 Studio 无网络仍可演示已有来源的导航、变化提醒、知晓与撤销。模型建议需要可用配置。

隔离界面预览：在 `packages/studio` 执行 `node tests/fixtures/trace-preview-server.mjs`，打开 `http://127.0.0.1:41739/tests/fixtures/trace-preview.html`。这使用真实组件与 store，但模型和文件操作是测试替身，应明确标注，不能当作实际模型表现。
