# Trace 功能演示与组会讲解

## 1. 汇报主线

用一句话介绍：把论文中的“需求到形式化规格的关联恢复”，接入 Studio 的日常编辑，让用户知道改动影响哪里，并在预览后决定如何同步。

主线围绕一条 Borrow 需求展开：建立关联 → 改需求 → 看到影响 → 预览并应用规格修改 → 撤销 → 反向同步。不要把全部高级功能挤进主演示。

## 2. 会前准备

在仓库根目录运行 `studio.bat` 启动源码开发版。若演示已安装的旧版程序，新的入口不会自动出现。

准备一个独立的演示目录，将 `examples/library-informal.aspec` 与 `examples/library-system.asfl` 复制进去，避免修改仓库原始样例。在 Studio 中“打开项目文件夹”选择该目录，并打开这两个文件。在 Hybrid 中选择包含 Borrow 的 `SYSTEM_Library` 模块；两侧文件都应已保存。

样例是语言展示文件，不应把它的全部规格当作已经验证正确。为了让主演示从清晰的一致基线开始，先把 Borrow 的第一个 FSF 分支从：

```text
member_id > 0 && success = 1 ||
```

改为：

```text
member_id > 0 and book_id > 0 && success = 1 ||
```

将 Informal 的 Borrow 描述写清楚：

```text
A member borrows a book when member_id > 0 and book_id > 0.
Return success = 1 when both conditions hold; otherwise return success = 0.
```

保留 Borrow 下原有 Inputs / Outputs 字段；相应调整描述中的重复规则，避免同一需求内出现矛盾。保存后再建立关联。

在 Studio 设置中配置可用模型，提前测试一次“AI 查找关联”和一次更新建议。模型响应会变化，演示前务必完整彩排；保存一份干净演示目录用于重来，另保留一份已确认关联的备份。备份整个项目，包括 `.agile-sofl/trace`，不要只复制规格正文。

## 3. 主演示：约 6 分钟

| 时间 | 操作 | 给观众看的结果 / 讲解词 |
|---|---|---|
| 0:00–0:40 | 打开 Informal / Hybrid 的“关联”，选中 Borrow | “这两个编辑器分别表达自然语言需求和形式化规格。关联是它们之间可检查的对应关系。” |
| 0:40–1:30 | 点击“AI 查找关联”；在“更多操作”确认候选范围为“全部 process（论文方法）”；查看推荐依据，接受 Borrow 对应 process | “恢复对象与论文一致：末级功能需求到 process，匹配时加入声明和依赖上下文。模型推荐后仍需审核。” 若手动建立，明确说这是人工基线，不是 AI 恢复结果。 |
| 1:30–2:10 | 将需求中的成功返回码从 1 改为 2；同步改掉 Borrow 描述中其他 success 1 的重复句 | 面板显示“需求已变更”。“正常输入只检测影响，不自动调用模型，也不改另一侧正文。” |
| 2:10–3:20 | 点击“建议更新 Hybrid →”，检查更新预览中的 before / after | 预期修改 Borrow 成功分支中的 `success = 1` 为 `success = 2`，失败分支保持 0。“建议范围、理由和具体差异都可见；我可以勾选修改再应用。” 模型如未提出修改或提出不合理修改，现场解释并拒绝，不强行应用。 |
| 3:20–4:00 | 点击“应用所选修改”，查看 Hybrid；使用全局撤销按钮或 Ctrl+Z，再重做 | 正文和关联基线一起撤销 / 重做。“接受建议是可回退的编辑动作，部分应用仍保持待检查。” 注意离开 Monaco / 文本输入焦点后使用全局历史，避免只演示输入框自己的撤销。 |
| 4:00–5:00 | 先确认两侧成功码都是 2，再把 Hybrid Borrow 成功分支改回 1；点击“← 建议更新 Informal”并预览 | “形式化规格先变也能反向生成需求修改建议，方向由用户决定。” 只在预览合理时应用。 |
| 5:00–6:00 | 展开“查看依据与变更”“检查约束”，打开“关联图”，点端点定位 | “关联确认、是否发生变化、约束覆盖结论是三件不同的事。模型找到支持证据不等于形式化证明。” 最后点击“保存规格文件”。 |

如筛选后看不到关系，先清除搜索、将“选中节点”改为“全部节点”，检查范围与“显示已拒绝”。如入口提示无文件对，检查是否在项目中打开并保存两类文件，以及当前模块对应 Hybrid 是否已打开。

不建议把“所有待检查数量必须变成 0”作为成功标准。只处理当前 Borrow 关系，其他共享声明关联仍可能需要独立检查。

## 4. 有余时再选一个扩展演示

- **拆分需求（约 2 分钟）**：选择 Borrow，打开“拆分 / 合并需求”，拆成“借阅成功条件”和“失败返回规则”。先预览新正文，再把原 Borrow 的关联明确分配给两个新需求，应用后展示一次撤销。说明系统不会擅自猜测拆分后关系。
- **稳定身份（约 1 分钟）**：在可视化表单中给 Borrow 改名，观察已确认关联仍能定位。文件唯一且内容不变的移动可以恢复身份；移动并改内容的情况用“重新定位文件”检查，不宣称任意重构都能自动识别。
- **并发审核（约 2 分钟）**：提前准备同一基线导出的两份审核快照，再演示“对比审核快照”的冲突选择。它合并审核决定，不自动合并两份规格正文。

## 5. 网络不可用时的备用演示

真实 Studio 仍可演示：手动建立关联、双侧定位、修改后的影响状态、拆分 / 合并以及撤销。主动说明 AI 部分本次未在线运行。

隔离界面预览可在 `packages/studio` 目录运行：

```powershell
node tests/fixtures/trace-preview-server.mjs
```

然后打开 `http://127.0.0.1:41739/tests/fixtures/trace-preview.html`。该页面用真实 Vue 组件和 store，但后端、模型结果与文件操作为测试替身，只用于说明界面交互。不能把它录制成真实模型或真实文件持久化的效果。

## 6. 组会讲解结构：约 10–12 分钟，含演示

1. **问题（1 分钟）**：同一需求在两种表达中存在，改了一侧后，用户很难确定另一侧哪里需要复查。单次生成缺少持续维护关系。
2. **论文方法（1 分钟）**：需求分解树提取末级功能，解析 process 及依赖上下文，LLM 恢复语义关联。论文评估的是关联恢复；双向编辑、审核和恢复是本项目的产品扩展。
3. **交互原则（1 分钟）**：正常编辑不打扰；只标记影响；AI 由用户触发；修改必须预览；正文与关联一起可撤销。
4. **现场演示（6 分钟）**：照上表完成一条 Borrow 的闭环，最多加一个扩展场景。
5. **实现与验证（1–2 分钟）**：项目级实体 UUID 和依赖索引；关联审核、变更基线、覆盖检查分离；版本校验与可恢复事务防止旧建议覆盖新输入。当前提交前 Studio 67 个测试文件、291 项测试通过，生产构建和模块边界检查通过；全量类型检查仍有仓库既有问题。
6. **研究验证下一步（1 分钟）**：标注独立的真实项目数据，分别测关联恢复 P/R/F1，以及更新建议接受率、人工修改量、任务完成时间、错误覆盖次数。不能用单元测试通过率代替模型质量。

建议开场原话：

> 我这次把论文里的 trace-link 恢复方法接到了 Agile SOFL Studio。重点是让关联在持续编辑中可用：改需求以后，用户能看到哪些规格需要检查，再决定是否采用 AI 建议。下面我用一个借书返回码变化演示从发现影响到审核应用的完整过程。

建议收尾原话：

> 目前已经打通关联恢复、影响检测、双向建议和人工审核应用，并加入结构变更、撤销及恢复机制。工程测试通过，但真实模型的准确率和对用户效率的提升还需要独立实验评估。下一步会把关联质量和编辑任务效果分开测量。

## 7. 老师可能问的问题

| 问题 | 建议回答 |
|---|---|
| 和论文相比新增了什么？ | 论文提供恢复关联的方法；这里把它放进连续编辑流程，新增变更状态、双向建议、预览应用、身份维护、审核冲突和恢复。尚不能称为经过用户实验验证的研究改进。 |
| 为什么不直接自动同步？ | 两侧可能都改了，也可能一个需求对应多个 process。先提供影响和证据，再让用户决定更新方向与范围，减少错误覆盖。 |
| 有关联就说明规格正确吗？ | 不能。关联只表示对应关系；约束检查另存结论与证据，LLM 判断也不能替代形式化证明。 |
| 是不是只是按名字匹配？ | 默认让模型基于需求、process 和声明依赖做语义判断；名字基线只作为离线评估对照。实际恢复质量仍需要标注实验。 |
| 改名、拆分以后怎么办？ | 用稳定 UUID 维护身份，明确改名操作保留关系；拆分 / 合并逐条分配关联。无法唯一判断时保留待检查，不静默换绑。 |
| 有没有达到论文指标？ | 尚未实测。论文中的指标属于论文项目，不能转移到本系统；当前合成评估用例只验证评估管线。 |
| 更新会不会覆盖正在输入的内容？ | 应用前复核 revision 和源文本；过期方案拒绝应用。多文件保存有持久日志可恢复，但不是文件系统级跨文件瞬时原子提交。 |

实现细节和边界参见 [Trace 关联与双向联动](./26-Trace关联与双向联动.md)。
